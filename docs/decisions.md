# Design decisions

Short records: what was chosen, the alternatives, and why. One entry per stage.

## Stage 0: repository skeleton (2026-11-01)

- **Chosen:** one Python package (`documind/`) at the repo root with `pyproject.toml`;
  `frontend/` kept separate for React + TypeScript.
  **Alternatives:** a monorepo with separate `backend/` and `frontend/` projects; a
  `src/` layout. **Why:** the API, ingestion, retrieval and eval scripts all share one
  codebase; a flat package keeps imports and Kaggle reuse simple.
- **Chosen:** README metric tables are generated by `scripts/render_readme.py` from
  `results/*.json`; a missing value is `TBD`. `--check` lets CI fail when the README is
  stale. **Alternatives:** hand-written tables; a notebook that prints results.
  **Why:** makes it impossible to put a number in the README that no script produced.
- **Chosen:** configuration via environment variables with `pydantic-settings`
  (`DOCUMIND_` prefix), `.env` git-ignored, `.env.example` committed.
  **Alternatives:** YAML config files. **Why:** the API key must stay out of git, and
  Docker Compose passes env vars natively.

## Stage 1: ingestion (2026-11-01)

- **PDF parsing: PyMuPDF text blocks.** Alternatives: pdfplumber, pypdf, unstructured.
  Why: fast on CPU, gives paragraph blocks with bounding boxes (needed for highlighting
  in stage 4), and renders pages for OCR with the same library. Note: PyMuPDF is AGPL;
  this matters if the service is offered to third parties (open question in issues).
- **Scan detection: a page with < 30 extracted characters is OCR'd.** Alternatives:
  image-area ratio, OCR everything. Why: simple and cheap; pages with a broken text layer
  (garbage characters) are not detected yet (open issue).
- **OCR: tesseract with the combined `uzb+uzb_cyrl+rus` model at 300 dpi.** Alternatives:
  one model per page after language detection; EasyOCR / PaddleOCR (heavier on CPU, weaker
  Uzbek support). Measured on synthetic scans (`results/ocr_synthetic.json`): the combined
  model had lower CER than the single "correct" model, most visibly for Russian (0.60% vs
  3.56%), because Russian contracts in Uzbekistan contain Latin-script names that the
  `rus` model garbles. Caveat: synthetic, mildly degraded scans; real scans will be worse.
- **Normalization: Uzbek apostrophe variants unified to ʻ (after o/g) and ʼ (elsewhere),
  one-to-one character replacement.** Alternatives: ASCII apostrophe everywhere; no
  normalization. Why: the same word appears as oʻ, o', o‘, o` in real documents and OCR
  output; matching needs one form, and the stored text stays human-readable.
- **Language detection: script majority, then Uzbek-only letters (ў қ ғ ҳ) vs Russian-only
  letters (ы щ), plus function words.** Alternatives: fastText lid / langdetect. Why: those
  models handle uz-Cyrl poorly and confuse it with Russian/Kazakh; the rule is transparent.
  Function words were added after OCR was seen to turn ў/қ/ҳ into у/к/х on some uz-Cyrl
  pages, which made those chunks look Russian.
- **Chunking: structure-aware (articles, chapters, numbered upper-case sections), greedy
  packing up to 180 words, no overlap, chunks never cross sections, each chunk is an exact
  span of the document text.** Alternatives: fixed-size token windows with overlap;
  semantic chunking with embeddings. Why: legal answers usually live in one article;
  exact spans make citation checks trivial; no overlap keeps `gold_chunk` labels
  unambiguous. 180 words keeps chunks under the 512-token limit of multilingual-e5-small.
- **Document ids from file names (or a manifest), not content hashes; sha256 for
  deduplication.** Why: eval labels reference `gold_doc`, so ids must survive
  regeneration of a file whose bytes change (e.g. DOCX timestamps).
- **Split by document group, stratified by language, frozen in `data/splits.json`.**
  Alternatives: pure hash split (kept as the default for new documents); random split.
  Why: translations of the same act must not end up in train and test (leakage); with a
  small corpus the hash split was unbalanced (1 of 12 uz-Cyrl documents in test).
- **Synthetic uz-Cyrl text is transliterated from the uz-Latn templates.** Alternative:
  writing separate Cyrillic templates. Why: less effort, consistent content. Bias: real
  Cyrillic documents differ in spelling and vocabulary, so uz-Cyrl results on synthetic
  data are optimistic.

## Stage 2 prep: real documents (2026-11-01)

- **Chosen:** a source registry (`data/sources.json`) as the single source of truth;
  `scripts/fetch_sources.py` downloads only entries marked `approved` (license, who
  checked, when) and generates the table in `docs/data.md`. Files can also be placed by
  hand in `data/raw/`. **Alternatives:** a hand-maintained list in `docs/data.md`; a
  scraper. **Why:** the terms check becomes a hard gate in code, and the documentation
  cannot drift from what was actually downloaded (sha256 recorded).
- **Chosen:** split strata = kind (real / synthetic) + languages of the group.
  **Alternatives:** one pool for all documents; excluding synthetic documents from the
  split. **Why:** real results must not depend on how many synthetic documents exist, and
  a law published in uz and ru is one group, so its two versions never straddle train/test.
- **Open:** no real document could be included: lex.uz and other sources are blocked from
  the build environment, so their terms could not be read.

## Stage 2: retrieval baselines (2026-11-01)

- **BM25: own small implementation (Okapi, k1 = 1.2, b = 0.75) with selectable analyzers.**
  Alternatives: rank_bm25, Elasticsearch/OpenSearch, PostgreSQL full-text search.
  Why: a few dozen lines, no extra service on the CPU server, and full control over
  tokenization, which matters most for Uzbek.
- **Analyzer `fold+stem6` as default:** apostrophes removed, Cyrillic mapped to Latin with
  OCR-confusable letters merged (қ/к, ҳ/х, ғ/г, ў/о), tokens cut to 6 characters.
  Compared on the **train** split only (synthetic set; plain, fold, ±stem5/stem6): with
  stemming Recall@5 rose from 0.949 to 1.000 and MRR from 0.864 to 0.907; fold vs plain
  differed little. Caveat: the synthetic set is near saturation and scripts are not
  mixed between query and document there, so this must be re-checked on real questions.
  Alternatives: Snowball stemmers (no Uzbek), a morphological analyzer (Apertium uzb).
- **Dense: multilingual-e5-small as ONNX, run with onnxruntime; model revision pinned.**
  Alternatives: sentence-transformers with PyTorch; e5-base / bge-m3 (larger, slower on
  CPU). Why: no PyTorch on the server, ~10 ms per query on 4 CPU cores in this
  environment, 384-dim vectors. The fine-tuned model from Kaggle (stage 5) must be
  exported to ONNX the same way.
- **Vector store: Qdrant, in-process (`:memory:`) for evaluation and tests, server via
  `DOCUMIND_QDRANT_URL` in deployment; same code path.** Alternatives: pgvector, FAISS,
  plain numpy. Why: Qdrant is the planned deployment component; filters by document
  are needed for "ask about this file".
- **Hybrid: reciprocal rank fusion, k = 60, 100 candidates from each retriever.**
  Alternatives: weighted score fusion (needs score normalization and tuning).
  Why: parameter-light and robust when the two score scales differ.
- **Evaluation: Recall@1/5/10 and MRR@10 per question set, 95% bootstrap confidence
  intervals, per-language breakdown; real and synthetic sets are separate files, separate
  corpora and separate README tables.** Settings are chosen on the train split and
  reported on the test split.
- **Synthetic questions use "document" scope (search within the gold document).**
  Why: the synthetic contracts are near-identical templates, so a question without names
  has many equally correct answers across documents. This makes the synthetic numbers
  a pipeline sanity check only. Real questions use "corpus" scope.
- **Question drafting without an LLM** (heading-based and number-based drafts), with a
  review step that refuses unedited drafts. Alternatives: LLM-generated questions (better
  wording, but they need the API budget guard from stage 3 and tend to copy the passage).
  Why: drafts only save typing; the questions you write decide the result.
- **Observation (synthetic test set):** BM25 is weakest on Russian (Recall@1 0.66) and e5
  is weakest on uz-Cyrl (Recall@1 0.73; the uz-Cyrl text is machine-transliterated);
  hybrid evens this out. Differences overall are within the confidence intervals.

## Stage 2: real documents (2026-11-02)

- **HTML instead of PDF for lex.uz acts.** lex.uz offers no PDF for the Civil Code, and
  its Word export is a JavaScript action. Chosen: a small parser for the act pages
  (`documind/ingestion/lexuz_html.py`, standard-library `html.parser`) that maps chapter
  and article headings to heading blocks and paragraphs to text blocks, and keeps each
  element's lex.uz id for citation links. Alternatives: PDF where available (inconsistent
  across documents, layout noise); converting by hand (not reproducible). Tests use a
  handwritten sample, never lex.uz text.
- **Editorial amendment notes are skipped** (lex.uz marks them `lx_no_select`: amendment
  history, cross-reference indexes, "changes origins"). Why: they are not part of the
  legal text and would add near-duplicate passages ("in the wording of the law of ...").
  Limitation: questions like "when was article N amended?" cannot be answered.
- **Uzbek in Latin script for both acts** (lex.uz's own Latin publication).
- **Deviation from the document-level split: chapter-group split for the real acts.**
  With only two acts, splitting by document (with uz and ru kept together) would put one
  whole act in test and the other in train. Chosen: the same chapter in both language
  versions of an act forms one split group (`<act>/ch<N>`), stratified per act (~30 % of
  each act's chapters in test). Translations of the same chapter never straddle the
  split, so there is no translation leakage. **Limitation:** train and test share the
  same acts, vocabulary, drafting style and cross-references between chapters, so test
  results (and especially fine-tuning gains) will look better than on an unseen act.
  Mitigation planned: a held-out third act (consumer protection law) as an
  out-of-domain test set.
- **Splits are stored per chunk** (`chunks.split_group`, `chunks.split`); a document
  split by chapter has `documents.split = "mixed"`. Evaluation, drafting and future
  training-pair generation use the chunk's split.
- **Civil Code test chapters pinned by topic: 29 (sale), 34 (rent), 37 (contract work,
  incl. construction).** Decided by topic and size on 2026-11-02, **before any labeling
  or evaluation on real data**. The hash split had put all three in train. They are much
  larger than the chapters the hash split had chosen (about 23.5k, 11.3k and 13.4k words
  for uz + ru, against at most 5.7k), so a three-for-three swap would have raised the
  Civil Code test share to 46 % of its words. Chosen instead: the Civil Code test set is
  exactly these three chapters (31.4 % of its words; the other 40 chapters are train).
  The Labor Code keeps its hash-based chapter split (10 of 34 chapters, 28 % of words).
  Recorded in `data/splits.json`. **Limitation:** the Civil Code test set covers only
  three chapters (sale, rent, construction work), so results may not generalize to other
  parts of the code.
- **Version check before labeling:** `scripts/compare_versions.py` compares the uz-Latn
  and ru Civil Code article by article (paragraph count and the numbers in the text,
  because the two pages show different edition dates). One article (888) differs; it is
  listed in `docs/data.md` and should not be used for questions. Wording changes that
  keep all numbers are not detected.

## Fix: Latin homoglyphs in Cyrillic words (2026-11-02)

- **Found:** the Russian Civil Code page from lex.uz contains 141 words in 85 chunks with
  Latin letters inside Cyrillic words ("пеpвой" with a Latin "p", "cтоимоcть" with a Latin
  "c"). Such words do not match their normal spelling in BM25 and tokenize differently
  for the embedding model. The other three documents had none.
- **Chosen:** a normalization step (`fix_cyrillic_homoglyphs` in
  `documind/ingestion/text.py`) that replaces Latin look-alike letters
  (a c e o p x y k and A B C E H K M O P T X Y) with their Cyrillic equivalents, **only in
  words that already contain a Cyrillic letter, and only if every Latin letter in the
  word has a look-alike**. Purely Latin words (uz-Latn text, company names) and words
  with other Latin letters (e.g. "Тexno") are left unchanged. Alternatives: fixing the
  documents by hand (not reproducible); folding in the BM25 analyzer only (would not help
  the embedding model or the displayed text).
- **One character for one character**, so offsets are unchanged. After re-ingesting the
  Russian Civil Code: 0 mixed-script words (was 141); chunk ids, offsets, chapters,
  word counts, languages and the train/test split are identical; only the letters
  p→р and c→с changed in 85 chunks; the synthetic eval results are identical.

## Evaluation: article-level secondary metric (2026-11-04)

- **Chosen:** chunk level (the gold chunk itself) stays the **primary** metric.
  An **article-level** metric is reported next to it as a **secondary** one: a result
  counts if it is any chunk of the gold article in any language version of the act.
  Chunks outside a numbered article fall back to chunk-level matching.
- **Added after seeing the pilot results** (10 real questions, `docs/experiments.md`), not
  planned in advance. The pilot showed two kinds of misses that are arguably not
  retrieval failures: a neighbouring chunk of the same long article, and the same
  article in the other language (e.g. a uz-Latn question whose first result was the
  Russian version of the gold article). The strict metric counts both as misses.
- **Why keep the strict one as primary:** the answer and citation are built from the
  retrieved chunk, so the exact passage matters; the article-level number is an upper
  bound that shows how many misses are "right article, wrong passage or language".
  Alternatives: marking both language versions as gold in the labels (more labeling
  work, still misses neighbouring chunks); restricting search to the question's
  language (hides cross-language behaviour).
- **Pilot results stay out of the README.** The README's real table shows results only
  from 80 labeled questions on; smaller samples are documented in
  `docs/experiments.md` (tables generated by `scripts/render_experiments.py`).

## Pilot error analysis: no changes to test questions or analyzers (2026-11-04)

Two pilot questions were found by no method; both were analyzed read-only and left as
written by the annotator.

- **"Menga ishda qoʻl koʻtarishdi kompensatsiya talab qilsam boladimi?"** (gold: Labor Code
  article 565, `labor-code-2022-uz#c0738`). Article 335 (`labor-code-2022-uz#c0451`,
  moral damage caused by the employer's unlawful actions, compensated in money) answers
  it about as well. **Not added as a second gold:** article 335 is in a train chapter
  (19) that will be used for fine-tuning pairs, so making it a test gold would
  contaminate the test set. The question is tagged `ambiguous-gold` instead, so its
  effect can be read in the per-tag results.
- **"Ijtimoiy tatildan bosh tortib uning oʻrniga pul olsam boʻladimi?"** (gold: article
  239). No other chunk answers it as well (article 234 is about annual, not social,
  leave). BM25 missed it partly because prefix stemming at 6 characters cuts inside the
  suffix of a 5-letter root: "tatildan" → `tatild`, but "taʼtillarni" → `tatill`; and
  "pul" ≠ "pulli".
- **No analyzer is tuned on these test questions.** Stem length, synonyms and similar
  settings will be tuned only on a separate dev question set from train chapters (see
  `docs/issues.md`).
